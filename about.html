I'm Badr — a cybersecurity graduate with a strong interest in web privacy and performance. I built PixelSqueeze because I was frustrated with existing image compression tools that require uploading your files to a server. When you work with sensitive images — medical photos, ID documents, personal photos — the last thing you should have to do is hand them to a third party. I knew the browser was capable of doing this work locally, so I built a tool that proves it.

My background in cybersecurity means I think hard about trust models and threat surfaces. The fundamental architecture of PixelSqueeze — no backend, no file storage, no user accounts — isn't just a feature; it's a deliberate design choice that eliminates entire categories of risk.

Why PixelSqueeze Exists

In 2024, there are dozens of image compression websites. Most of them upload your files to a server, process them, let you download the result, and then (they claim) delete the file after a few hours. Whether or not that deletion happens, you've already transmitted your image data over the internet to infrastructure you don't control. For a cat photo, that's fine. For a passport scan or a medical report, it shouldn't be necessary.

Modern browsers have matured to the point where professional-grade image processing is possible entirely in-browser. The Canvas API, createImageBitmap(), OffscreenCanvas, and Web Workers give front-end developers the tools to compress, convert, and resize images with the same results as server-side tools — without any network transmission.

PixelSqueeze is my attempt to build the tool I wanted to use: fast, clean, private by design, and free with no strings attached.

How Browser-Only Processing Works

Here is exactly what happens when you drop an image into PixelSqueeze, with no steps omitted:

  1. File reading: JavaScript's File API gives the browser access to the selected file as raw bytes. Nothing is transmitted anywhere.
  2. Decoding: createImageBitmap(file, { imageOrientation: 'from-image' }) decodes the compressed image into raw pixel data (RGBA values). The imageOrientation option reads the EXIF rotation tag in phone photos so portrait images appear correctly.
  3. Rendering: The decoded bitmap is drawn onto an OffscreenCanvas (in a Web Worker) or regular <canvas> (fallback). For JPEG output, the canvas background is pre-filled white to replace any transparency. For PNG, UPNG.js performs color quantization (reducing the palette from 16M colors to as few as 16) for real size reduction.
  4. Encoding: canvas.convertToBlob() or canvas.toBlob() re-encodes the pixel data to the target format and quality. For the "target KB" feature, this step is repeated up to 12 times with a binary search over quality values until the output hits your target.
  5. Download: The encoded blob is given to you as a download via a temporary blob:// URL that is revoked after use. The original file and all intermediate canvases are garbage-collected by the browser.

At no point in this process does any data leave your browser tab. There is no WebSocket, no XMLHttpRequest, no fetch call to any server. The network tab in your browser's DevTools will show zero image-related network requests during processing.

Technology Stack

PixelSqueeze is intentionally built with a minimal, dependency-light stack:

  • HTML, CSS, Vanilla JavaScript (ES Modules) — no framework, no build step, no node_modules. The entire site is static files that deploy in seconds.
  • Web Workers + OffscreenCanvas — heavy image processing runs on a background thread, keeping the UI responsive during batch processing.
  • UPNG.js — for real PNG color quantization, self-hosted from this site.
  • JSZip — for creating ZIP archives of batch-processed images, self-hosted from this site. If unavailable, files download individually.
  • Inter (self-hosted) — clean, modern typography, served from this site with font-display: swap.
